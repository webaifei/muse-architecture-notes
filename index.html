一个 AI 助理的权限，该给到哪一步

作者： 饭团儿

日期： 2026年10月6日

Muse 是 Meta 上个月发布的个人 AI 助理。它跑在你自己的一台云电脑里，能读邮件、改日历、开浏览器、执行命令。

大多数介绍只讲它能干什么。但它出错的时候，最多能错到哪一步，很少有人问。

本文先用一个能跑起来的实验，说明"给 agent 加权限检查"这条路为什么走不通，再看 Muse 换的那条路。

一、先写一个检查

假设你的助理能读文件，但只允许读工作区里的。

最直觉的写法是加一道检查。

function check(path) {
  return resolve(WORKSPACE, path).startsWith(WORKSPACE)
}

把输入拼成完整路径，看它是不是以工作区开头。

下面把它跑起来，连试三个输入。


输入 readme.txt
  检查 通过
  读到 这是工作区里的公开文件

输入 ../secret.txt
  检查 拒绝
  读到 （无）

输入 innocent-link.txt
  检查 通过
  读到 ghp_REAL_SECRET_TOKEN_abc123
  【机密泄露】

上面代码中，第二条被挡住了，因为 resolve 会先把 .. 消掉，路径就跳出了工作区。

第三条没挡住。innocent-link.txt 是一个符号链接，它自己确实躺在工作区里，但它的目标在外面。

所以这道检查做对了它以为自己在做的事，却漏掉了一个它没想到的情况。

二、把符号链接解开

漏在哪儿，补哪儿。既然检查比对的是字符串，那就先把它变成真实路径再比。

const real = realpathSync(join(WORKSPACE, path))
return real.startsWith(WORKSPACE)

再跑一次。


输入 innocent-link.txt
  前缀匹配       通过，然后泄露
  真实路径解析   拒绝
  真实路径是     /private/tmp/muse-check-experiment/secret.txt

上面代码中，两条检查给出相反的答案。差别在于第一条看的是链接文件自己，第二条看的是它指向哪。

这一层修好了。

顺便说一个我自己踩的坑。写这个实验时，第二版一开始还是漏的。原因是 macOS 上 /tmp 是 /private/tmp 的符号链接，工作区根目录本身没解析，比对的两边一个带 /tmp、一个带 /private/tmp，怎么都对不上。

修法是多解析一次根目录。

const ROOT = realpathSync(BASE)
const WORKSPACE = join(ROOT, 'workspace')

下面接着看第三层。

三、检查通过了，文件被换掉

第二版是这样写的：先解析真实路径，确认在工作区里，然后打开它。

问题是，解析和打开是两次独立的操作，中间隔着时间。

下面这段代码把那个时间差显式露出来。

function safeOpen(path, { betweenCheckAndOpen } = {}) {
  const full = join(WORKSPACE, path)
  if (!realpathSync(full).startsWith(WORKSPACE)) {
    return { blocked: true }
  }
  betweenCheckAndOpen?.()        // ← 攻击窗口
  return { content: readFileSync(full, 'utf8') }
}

正常读取没有问题，读到的是"无害内容"。

如果攻击者在这个窗口里把 slot.txt 换成一个指向机密的符号链接，检查看到的是换之前的那个文件，打开的是换之后的那个。


正常情况
  读到 无害内容

被攻击时
  读到 ghp_REAL_SECRET_TOKEN_abc123
  【检查通过，读到的却是机密】

上面代码中，两次调用用的是同一个函数、同一份工作区，唯一区别是中间有没有人动手脚。

这一类问题有个名字，叫 TOCTOU（检查时间和使用时间不一致）。修法也有名字：先打开文件，再对已经打开的句柄做检查，中间不留窗口。

四、这一层不是漏洞

前面两个漏洞都能修，第二个的修法也是标准做法。

但我想说的不是"检查很难写对"。

真正的问题是这两个字：同一个进程。

检查函数、策略表、路径解析用的 API、被检查的文件操作，全都跑在 agent 自己的进程里。

下面三件事，在这个前提下必然成立。

（1）策略表是内存里的一个变量，agent 读得到，也改得掉。

（2）检查用到的函数，agent 能替换掉。

（3）检查只是一段代码，agent 能绕过它，直接调底层。

所以每修一层，就多出一层要守着。守卫住在被看守的人隔壁。

Muse 没在这条路上继续修，它换了个问法：能不能让 agent 那一侧根本够不着。

下面看它怎么做。

五、两个域

Muse 跑在用户专属的一台云 VM 里，这台 VM 被切成两个区。

一个叫 runtime cell，就是跑 agent 本体的那个容器，加上工作区、文件、所有工具和二进制。本文中又称"不可信域"，也就是上面那个实验里检查函数待的地方。

一个叫 host domain，里面是各种安全服务：查提示注入的分类器、凭据保管、连接器 worker，还有一个叫 Sentinel 的裁决器。本文中简称"控制面"，也就是上面那些检查逻辑应该待的地方。

agent 在第一个区，裁决权在第二个区。

官方文档里有一句话概括这个设计。

The right mental model is two isolated security domains on one box, not an LLM powered agent with root.

正确的理解是"一台机器上的两个隔离安全域"，不是"一个有 root 权限的 LLM"。

还有一句更关键。

This split is important as the runtime cell is expected to process untrusted data.

这个切分很重要，因为 runtime cell 预期会处理不可信数据。

不是"万一被攻破怎么办"，是"假设它会被攻破"。

那么问题就来了：假设它被攻破，凭什么还能保证安全。

下面看四个具体机制。

六、容器里的 root

Linux 有一种东西叫 user namespace，它维护一张 uid 映射表。

你在里面看到自己是 0 号用户，也就是 root。但内核做权限检查时，用的不是 0，而是映射表另一头的数字。

下面这张表说明了映射关系。

namespace 内    宿主上
   0      →      100000
   1      →      100001

上面这张表的意思是，容器里的 0 号用户在宿主上其实是 100000 号，一个普通用户。

所以你在容器里装包、改文件属主，看起来都是 root 在干，但真正的权限检查落在宿主那个普通用户身上，直接拒绝。

官方原话是：

Root inside the runtime cell is mapped to an unprivileged host user so runtime cell root is not host root.

这一条为什么重要，想想第一节那个实验就明白了。容器逃逸的经典路径，是先在容器里拿到 root，再找个内核漏洞打成宿主 root。

有了上面那张映射表，就算拿到容器内 root，宿主那边你还是 100000 号。

七、系统调用

第二个机制叫 seccomp。

一个进程可以往内核里装一小段程序。此后它每次发起系统调用，内核都先跑这段程序，再决定放行还是拒绝。

返回 ALLOW 就放行，返回 ERRNO 就当这个调用不存在，返回 KILL 就直接杀进程。

下面这两条性质值得注意。

第一，只能收紧，不能放松。装上去就撤不掉，也不能再开新的白名单。

第二，它在内核里执行。被限制的进程没有办法绕开它，连发起那个调用的资格都没有。

Muse 用它关掉了一个东西：io_uring。

It also gets ... filtered system calls (for example no io_uring).

io_uring 是 Linux 的高性能异步 IO 接口。它和普通系统调用不一样，提交任务不用每次陷入内核，而是写进一块共享内存的环形缓冲区，内核在后台自己取。

你可能要问，那为什么不直接过滤它，而要整个关掉。

因为它有两个麻烦。一是很多操作不走常规系统调用路径，按系统调用检查的传统手段看不到它。二是它自己历史上出过好几次严重漏洞，是容器逃逸的常见入口。

所以 Muse 直接把它关掉。

这个思路值得记下来。安全上遇到复杂的东西，第一反应不该是"怎么过滤它"，而是"我需不需要它"。

不需要就整个关掉，比逐条过滤可靠得多。

八、权限开关

传统 Unix 里 root 是一整块，要么什么都能干，要么什么都干不了。

Linux 把它拆成了大约四十个独立的开关，叫 capabilities。每个开关管一类特权。

CAP_SYS_PTRACE 允许你 ptrace 别的进程，也就是读别人的内存。

CAP_NET_ADMIN 允许你改网络接口、路由表和防火墙规则。

CAP_SYS_ADMIN 能 mount，能改 cgroup，实际上就是新的 root。

Muse 的容器丢掉了前两个。

... and limited kernel capabilities (for example no CAP_SYS_PTRACE and no CAP_NET_ADMIN).

CAP_SYS_PTRACE 必须丢，因为它直接威胁上面说的两个域。能读别的进程内存，就能读控制面的秘密。

CAP_NET_ADMIN 也必须丢，因为它威胁出口策略。能改路由表，就能绕过代理把数据发出去。

注意这两件事可以同时成立：你在容器里是 uid 0，同时你没有这两个开关。

权限被拆开之后，"是 root"这句话就不再有单一含义了。

九、通道

agent 总要和外面的服务说话。这里的问题是，服务端怎么确认对面是谁。

常见的做法是发一个 token。但 token 本身是个秘密，放在通道上就可能被偷。

Muse 用的是 Unix domain socket，加上一个叫 SO_PEERCRED 的机制。

它的工作方式是这样的。

服务端调用它，内核直接告诉服务端，连接过来的那个进程是谁，pid、uid、gid 全都有。

关键在于这个信息由内核填写，对端无法伪造。进程不能声称自己是别的 uid。

于是服务端可以据此做权限判断，而且通道上不需要放任何秘密。官方文档说：

All communication between the runtime cell and other services in the VM happens via Unix domain sockets with SO_PEERCRED and peer ACLs. This provides kernel authenticated, least-privilege interprocess communication with no secrets to steal.

最后四个词是重点：没有可偷的秘密。

如果一个通道本身不含秘密，那它就没有可偷的东西。这和"我们不把秘密告诉别人"是两码事。

它起两个进程。一个扮演 host domain，持有凭据，只暴露一个接口。另一个扮演 runtime cell，跑在操作系统沙箱里，通过 Unix socket 和前者说话。

十一、回到那个实验

拿第十节的输出，和第一节的实验对照一下。

第一节的检查被绕过，是因为攻击者能改那个策略变量、能换掉那个函数。

第十节的控制面没有 grant 这个操作。不是"它检查后拒绝了"，是"没有那条代码路径"。

这两件事差别很大。

拦截式的做法，写一段检查逻辑，发现越权就返回错误。它被绕过的前提是检查有漏洞。

无路径式的做法，干脆不实现那个能力。它被绕过的前提是找到一段不存在的代码。

代码越长，第一种做法越危险。你新增一条调用路径，就有可能忘了在那里加检查。

第二种不存在这个问题。

所以 Muse 那四个机制，没有一个是"更严格的检查"。

它们全都是"拿不到"。

二、提议不是命令

代码：code/step2-action-proposal.mjs
官方来源：How We Built Safety Into Muse

我原以为给模型一个 JSON Schema 就够了

模型输出 JSON，我用 schema 校验一下，通过了就执行——这是我以前的写法。

问题不在"校验了没有"，在于校验通过之后你拿什么去执行。

如果你执行的是模型给的那个对象，那么：

  • 它上面可能有校验时没看的字段
  • 它的原型链上可能有东西
  • 下游任何一次 Object.assign / 展开 / 递归合并，都可能把没检查过的东西带进去

Muse 的做法是：模型的输出从来不会被直接执行，它只是一份提议（proposal），经过边界校验后重新构造成内部对象，才进入后续流程。

官方怎么说

When Muse wants to take action via a connector, the relevant connector tool is invoked in the runtime cell. That submits a request to Sentinel describing the connector, which method is to be invoked, the class of action, its scope, and context of what the user asked for — from which Sentinel generates a user-visible purpose.

注意它描述的是一个结构化请求：connector、method、action class、scope、用户上下文。五样东西，每一样都是有限的、可枚举的。

模型不能"提议一个动作"，它只能"从已声明的方法里挑一个"。

技术 1：能力发现 —— 没声明的东西不存在

官方在讲 GitHub 例子时列的第一道判断：

能力发现：Skill 是否定义 list/read repository → 未定义则不可调用

原理：每个 connector 有一份 manifest，显式列出它支持哪些方法、每个方法的参数是什么。模型看到的工具列表是从这份 manifest 生成的；执行侧校验也查同一份 manifest。

为什么这比"检查参数"更根本：

做法 攻击者需要什么
检查参数是否合法 找到检查逻辑的漏洞
检查方法是否已声明 让一个不存在的方法出现

第二种在结构上就不成立。github.delete_repository 如果没写进 manifest，那它不是一个"被拒绝的调用"，而是一个没有对应实现的字符串。

Demo 里对应的两条：

  ▸ 模型发明了一个方法
    🛑 拒绝 [unknown_method] "github" 没有声明方法 "delete_repository"
  ▸ 模型发明了一个 connor
    🛑 拒绝 [unknown_connector] 没有名为 "shell" 的 connector

第二条尤其重要——模型想访问 shell，但系统里没有 shell connector。它不是在请求一个被禁止的能力，而是在请求一个不存在的名字。

技术 2：字段白名单，不是黑名单

原理：校验字段时只有两种写法：

// 黑名单：拒绝危险字段
if (key === 'exec' || key === '__proto__') reject()

// 白名单：只接受已知字段，其余一律拒绝
if (!ALLOWED.has(key)) reject()

黑名单的问题是你得穷举所有危险的名字——而攻击者只需要找一个你没想到的。

Demo 里用的是白名单：

const PROPOSAL_FIELDS = new Set(['connector', 'method', 'args', 'scope', 'userContext'])
for (const key of Object.keys(raw)) {
  if (!PROPOSAL_FIELDS.has(key)) throw new ProposalRejected('unknown_field', ...)
}
  ▸ 模型发明了一个字段 exec
    🛑 拒绝 [unknown_field] 不允许的字段 "exec"

白名单的代价：新增字段时必须同时改这里，否则合法请求会被拒。这是故意的——它把"新增字段"变成一个必须显式做的动作，而不是一个可能被遗漏的检查。

技术 3：参数也要白名单 —— 越权常常藏在"多给一个参数"里

  ▸ 越权参数：给 list_repositories 塞一个 token
    🛑 拒绝 [unknown_arg] 方法 "list_repositories" 不认识参数 "token"

这条演示的是一个很实际的攻击模式。假设下游的 connector 代码写成：

const token = args.token ?? authd.getCredential('github')

看起来无害——"没传就用默认的"。但如果模型能传 token，它就能用自己的值覆盖掉宿主注入的凭据。

Muse 在 privsep 那层的说法正好命中这个：

Each worker is identified by its cgroup and has explicit credential allowlists. A calendar worker cannot ask authd for an email credential simply by changing a request parameter.

"改一个请求参数"是这条攻击面的统一描述。 防御方式也一样统一：参数集合必须白名单，多一个都不行。

技术 4：原型污染 —— 为什么返回新对象

JavaScript 有一个别处没有的东西：每个对象都有一条原型链。

const raw = JSON.parse('{"connector":"github","__proto__":{"isAdmin":true}}')

JSON.parse 会把 __proto__ 创建成一个普通自有属性（用的是 CreateDataProperty，不触发 setter）。所以：

  • Object.keys(raw) 会包含 __proto__ → 白名单检查能拦住
  • raw.__proto__ 返回的是那个自有属性值（自有属性遮蔽了 Object.prototype 上的访问器）

但如果校验函数返回原始对象，危险就转移到下游了。很多库会做这种合并：

function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object') merge(target[key], source[key])
    else target[key] = source[key]
  }
}

merge({}, raw) 走到 __proto__ 时，target[key] = ... 触发的是 setter，于是 target 的原型被改掉。如果 target 恰好是 Object.prototype（某些库的默认参数就是它），整个进程里所有对象都获得 isAdmin。

这就是 prototype pollution——一次污染，全局生效。

防御有两层：

  1. 拒绝未知字段（白名单），让 __proto__ 根本进不来
  2. 返回重新构造的对象，而不是原始输入

第 2 层在 demo 里是这么写的：

return {
  connector: raw.connector,
  method: raw.method,
  actionClass: method.actionClass,
  // 只从声明过的参数里取值，其余一律丢弃
  args: Object.fromEntries(declared.map((k) => [k, args[k]])),
  scope: ...,
  userContext: ...,
}

返回值的原型是全新的 Object.prototype，和模型的输入没有任何引用关系。 下游无论怎么合并、展开、序列化，都碰不到输入里的额外属性。

顺带一提：DeepSeek Harness 的 PTC 运行时也踩过同一个点，它的契约里写着命名空间必须用 null-prototype 构造，这样 __proto__、constructor 这类名字会被当普通属性处理——同一类问题的另一种解法。

技术 5：fail-closed，而不是 fail-open

看 demo 里校验函数的结构：

for (const key of Object.keys(raw)) {
  if (!PROPOSAL_FIELDS.has(key)) throw new ProposalRejected(...)
}

任何一步不通过就抛错，没有"尽力而为"的分支。

对比一下常见的 fail-open 写法：

try { validate(raw) } catch { /* 校验失败就算了，继续执行 */ }

这种代码在正常路径上测不出来，只有在被攻击时才暴露。

Muse 整个架构都是 fail-closed 的：Sentinel 的三态是 allow / deny / ask——没有"默认放行"这一档。拿不准就是 ask，而不是 allow。

Demo 跑出来

node code/step2-action-proposal.mjs

七条提议，一条通过、六条被拒：

  ▸ 正常提议                              ✅ 接受
  ▸ 模型发明了一个字段 exec                🛑 unknown_field
  ▸ 模型发明了一个方法                     🛑 unknown_method
  ▸ 模型发明了一个 connector               🛑 unknown_connector
  ▸ 越权参数 token                         🛑 unknown_arg
  ▸ 原型污染尝试                           🛑 unknown_field "__proto__"
  ▸ 参数超长                               🛑 arg_too_long

每一条被拒的提议，如果直接 dispatch，都会变成一个真实的越权动作。

这一章要记住的

模型的输出是数据，不是命令。

判断标准很简单：从模型输出到真实副作用之间，有没有一次"重新构造"？

  • 如果执行的是模型给的对象 → 你只是"检查"了它，它还是它的
  • 如果执行的是重新构造的内部对象 → 模型给的东西在边界上就已经不存在了

下一章讲 Sentinel：当提议已经干净了，谁来决定它能不能被执行。

三、Sentinel：授权不在对话里

代码：code/step3-sentinel.mjs
官方来源：How We Built Safety Into Muse

我原以为审批就是"弹个窗问用户"

用户点了允许，然后呢？

如果"用户已允许"这个事实存在某个变量里、或者某条消息里，那它就是一个可以被污染的输入。模型只要能在上下文里写一句"用户已经同意了"，剩下的就靠下游代码有没有检查。

Muse 的做法是：审批根本不经过对话。

官方怎么说

Sentinel sends that request directly to the Muse client, where a dialog is presented to the user directly within the client UI — not via their conversation with Muse — and their answer is routed directly back to Sentinel.

Approvals granted via the human in the loop system are strict capabilities, not conversational suggestions. They're bound to the particular connector/destination and use case.

两句话点出两件事：

  1. 通道不同：问题从 Sentinel → 客户端 → Sentinel，模型既看不见也改不了
  2. 性质不同：授权是一个 capability（能力凭证），不是一句建议

技术 1：capability，而不是 identity

传统的权限模型是 RBAC（基于角色）：你是管理员，所以你什么都能做。

capability-based authorization 换了个方向：授权是一张具体的票，票上写着能对什么做什么。

RBAC capability
授权粒度 主体（你是谁） 客体 + 动作（能对什么做什么）
检查方式 查你的角色 出示票，票面必须精确匹配
权限扩大 换个角色就行 得重新开票

Demo 里那张票长这样：

{
  connector: 'github',
  method: 'create_issue',
  actionClass: 'write',
  resource: 'repoA',          // ← 资源写死在票上
  kind: 'session',
  expiresAt: ...,
}

匹配逻辑必须逐字段精确：

if (g.connector !== proposal.connector) continue
if (g.method !== proposal.method) continue
if (g.actionClass !== proposal.actionClass) continue
if (g.resource !== undefined && g.resource !== context.resource) continue

为什么"精确匹配"而不是"包含关系"：包含关系（比如"票允许 github.* 就可以做任何 github 操作"）在实现时要处理通配符、前缀、大小写等一系列边界，每一个都是绕过点。精确匹配没有这些边界。

技术 2：五种生命周期

官方列了五种授权范围：

one-time, session-scoped, task-scoped, time-bounded, or perpetual permission

类型 什么时候失效 典型场景
one-time 用一次就废 发一条消息
session 会话结束 本次对话里读日历
task 任务完成 这个任务期间允许改这个 repo
time-bounded 到期 接下来 30 分钟
perpetual 用户主动撤销 读公开仓库

注意"谁决定用哪种"：官方说 Sentinel 决定给用户呈现哪几种选项。这不是用户体验问题——给用户一个"永久允许一切"的选项，等于把这个功能废掉。

Demo 里最直观的是 one-time：

── 3. 用刚才的授权：范围一致 → 放行 ──
  ✅ allow — 沿用授权 grant_1
── 4. 一次性授权已被消耗 → 第二次必须重新审批 ──
  ⏸ ask — 产生待审批 approval_2

用掉就作废，grant.used = true 一行的事。

技术 3：默认拒绝，没有"默认放行"

const policy = USER_POLICY[key] ?? 'deny'   // ← 没配过的一律拒绝

三态 allow / deny / ask 里没有第四档。这点很关键：很多系统的隐含默认是"没有规则就放行"，那样每新增一个 connector，在用户配置它之前就是一个敞开的门。

demo 里 shell.run 被显式 deny，其余没配的走审批。

四个攻击场景

攻击 A：拿 repoA 的授权读 repoB

✅ 被拦住：授权范围是 repoA，请求的是 repoB

这是 capability 模型的核心价值。票是有边界的。

攻击 B：用写授权做读操作

✅ 被拦住：授权绑定 actionClass=write，请求的是 read

actionClass 也是票面的一部分。用户批准"给这个 repo 建 issue"，不代表同意你读它的私有内容。

攻击 C：模型在对话里写"用户已经批准了" ← 这一条最重要

✅ 没有被放行，仍然走审批：approval_1
   对话里那句"用户已经同意了"对 Sentinel 没有任何效力——
   授权状态只存在于 Sentinel 里，模型改不了它，也读不到它

注意这不是"我们检查了那句话是不是假的"——是那句话根本没有进入决策路径。Sentinel 的授权状态存在自己的内存里，模型既没有读的接口，也没有写的接口。

"用户同意了"是一个事实，事实只能由产生它的系统来断言。

攻击 D：限时授权过期后继续用

✅ 被拦住：授权已过期，回到审批流程

expiresAt 在每次匹配时检查。这里有个实现细节值得注意：过期检查必须在授权时做，不能只在签发时做。

这一章要记住的

授权状态不应该出现在模型能读写的任何地方。

判断一个 agent 系统在这点上做得好不好，问一个问题就够了：

模型能不能让"用户已经允许"这件事变成真的？

如果答案依赖"我们检查了模型有没有撒谎"，那答案是能——只要它找到一个你没检查的路径。

下一章讲凭据：当动作已经被授权了，凭据怎么用而不被偷。

四、凭据代理：拿不到，比不泄露强

代码：code/step4-credential-proxy.mjs
官方来源：How We Built Safety Into Muse

我原以为安全的关键是"别把密钥说出去"

所以我在 system prompt 里写：绝不要泄露你的 token。 再加个输出过滤器，扫描有没有 ghp_ 开头的字符串。

这套东西的问题是：它假设模型能拿到 token，然后靠"它不说"来保护。

Muse 干脆不让它拿到。

官方怎么说

For all such requests, code in the runtime cell or a worker only ever sees a "surrogate" token, minted by authd. After the concrete network request is authorized, Sentinel will replace any surrogate tokens with the real credential, obtained from authd, at the network boundary.

The agent never sees real tokens, which means any attempt to coerce the agent to reveal the actual secrets via prompt-injection or otherwise is futile.

最后那个词是 futile（徒劳）。

技术 1：凭据代理化（credential surrogation）

一张图说清：

authd（保险箱）        真实凭据 ghp_REAL_...
    │
    │ ① 铸造一个占位符
    ▼
runtime cell            surrogate_github_o6kci...
    │
    │ ② 带着占位符发起请求
    ▼
出口网关                L4/L7 检查 + 授权判断
    │
    │ ③ 在边界处替换
    ▼
api.github.com          收到真实凭据

关键在 ③ 的位置：替换发生在网络边界，不发生在 cell 里。所以 cell 进程的内存中，从头到尾没有出现过那个真字符串。

这和"我们不在日志里打印 token"是完全不同的强度——后者是"我们保证不打印"，前者是"它压根不在那儿"。

技术 2：能力隔离靠"传出什么对象"

这是我在写 demo 时踩到、也最想讲清楚的一点。

第一版我写成：cell 持有一个 Authd 实例，Authd 上有 realCredentialFor() 方法。然后我在注释里写"cell 没法拿到真凭据"。

这是假的。 realCredentialFor 就在原型上，cell 只要调它就拿到了。

真正的做法是只把 facade 传进去：

function credentialFacadeFor(authd) {
  return Object.freeze({
    request(provider) {
      return authd.issueSurrogate('cell', provider)
    },
  })
}
const cell = new RuntimeCell(credentialFacadeFor(authd), gateway)

现在 cell 手里的对象只有 request 一个方法。realCredentialFor 对它来说不是"被禁止调用"，而是——它这一侧根本没有能调到的那个对象。

Demo 跑出来的验证：

▸ 攻击 C：cell 想直接向凭据服务要真 token
    cell 手里的凭据门面暴露的方法：request
    cell 手里有没有 Authd 实例？没有
    ✅ realCredentialFor 不在门面上...
做法 强度
在 Authd 上加权限检查 依赖检查逻辑没漏洞
只传 facade 依赖对象图里不存在那条边

区别在于：前者是行为约束，后者是结构约束。结构约束不会因为某人写了一个新方法而失效。

这也是整个 Muse 架构反复出现的模式——从第 1 步的"控制面没有 grant 接口"到这里，都是同一件事。

技术 3：分离"谁能看到"和"谁能使用"

Muse 的 privsep 章节里有一句总结（第 6 步会展开）：

privsep decides where credential-capable code executes; authd decides which credential material an authenticated caller may obtain; and Sentinel decides whether an action may be taken.

三个问题，三个不同的组件：

问题 谁回答
哪些代码能碰凭据？ privsep
这个调用者能拿到哪类凭据？ authd
这个具体请求能不能出去？ Sentinel

分开的理由：如果这三件事由一个组件回答，那它就是一个单点——攻破它，三个防护一起失效。分成三个之后，攻击者要同时在三个地方成功。

四个攻击场景

攻击 A：提示注入让模型念出凭据

被注入的模型输出："我的 token 是 surrogate_github_o6kcip0g"
✅ 泄露的是一个代理令牌

这个令牌能干什么？只有一件事：被出口网关在已授权的请求上替换。它不能直接用来认证（攻击 B 验证了这点），也不能反向查出真凭据。

这就是 futile 的实际含义——不是"我们拦住了泄露"，是"泄露了也没有价值"。

攻击 B：绕过网关直接拿代理令牌访问 API

✅ API 返回 401：Bad credentials

真 token 从未离开 authd。代理令牌在 API 那边不存在。

攻击 C：cell 直接向凭据服务要真 token

见上面的 facade 分析。

攻击 D：把请求发往未授权目的地

网关日志：{"destination":"evil.example.com","approved":false,"injected":false}
✅ 目的地不在白名单 → 不注入真凭据

注意这一条和第 5 步的出口网关是同一个机制的两面：替换凭据的同一个判断，也决定了请求能不能出去。

这两个动作必须绑在一起。 如果"检查目的地"和"注入凭据"是两段独立的代码，就会出现"检查通过了 A，凭据注入到了 B"这种组合漏洞。

这一章要记住的

安全设计里，"它做不到"永远比"它不会做"可靠。

  • "我们告诉模型不要泄露" → 依赖模型
  • "我们检查输出里有没有密钥" → 依赖检查逻辑
  • "它手里没有密钥" → 依赖物理事实

第三种不会因为提示词写得不好、检查代码有 bug、或者模型被注入而失效。

下一章讲网络出口——凭据替换发生的那个地方，以及它要防的 SSRF。

五、出口网关：检查的和使用的是不是同一个东西

代码：code/step5-egress-ssrf.mjs
官方来源：How We Built Safety Into Muse

我原以为 SSRF 防护就是拉个黑名单

不让你访问 127.0.0.1，不让你访问 169.254.169.254——黑名单一列，收工。

这个思路会死在两个地方：地址的写法和检查的时机。

官方怎么说

All of Muse's network egress is managed at the egress point by Sentinel. The forward proxy ... inspects both L4 and L7 information, such as hostname, resolved and final IPs, port, protocol, HTTP method, path, and the decoded request itself.

SSRF protections prevent requests that appear to target a public domain but resolve to an internal service.

第二句是整章的核心："看起来是公网域名"和"实际连到内网"可以是两个不同的东西。

技术 1：云元数据服务 —— 为什么这一步要做

先讲清威胁。169.254.169.254 是云厂商的实例元数据服务地址（AWS/GCP/阿里云等都是）。从 VM 内部访问它，能拿到：

  • 实例的临时凭据（IAM role 的 access key）
  • 用户数据脚本（可能含密钥）
  • 网络配置、实例身份

拿到它就等于拿到了这台机器在云上的身份。 而它恰好是一个"内网地址、无需认证、HTTP GET 就能读"的接口。

在 Muse 的场景下，这是最致命的 SSRF 目标：agent 被注入 → 访问元数据 → 拿到实例凭据 → 用这个凭据访问用户的云资源。

所以出口网关必须挡住它。

技术 2：IP 的多种写法

黑名单的第一种死法。下面六个 URL 全部指向 127.0.0.1：

写法 为什么等价
http://127.0.0.1/ 标准点分十进制
http://2130706433/ 十进制整数：0x7F000001 = 2130706433
http://0x7f000001/ 十六进制
http://0177.0.0.1/ 八进制段
http://[::ffff:127.0.0.1]/ IPv4-mapped IPv6
http://[::1]/ IPv6 loopback

还有 http://127.1/（省略中间段）、http://0/（0.0.0.0）等等。

防御方式：先规范化，再判断。

function normalizeHost(host) {
  const raw = host.replace(/^\[|\]$/g, '')
  if (/^(0x[0-9a-f]+|\d+)$/i.test(raw)) {
    const n = Number(raw)
    return [(n >>> 24) & 255, (n >>> 16) & 255, (n >>> 8) & 255, n & 255].join('.')
  }
  // ... 混合写法
}

Demo 结果：

  ▸ 十进制写法：127.0.0.1 = 2130706433
    🛑 阻断 — 解析到 loopback (127.0.0.1)
  ▸ 十六进制写法：0x7f000001
    🛑 阻断 — 解析到 loopback (127.0.0.1)
  ▸ IPv4-mapped IPv6
    🛑 阻断 — 解析到 loopback (::ffff:7f00:1)

注意第三个：URL 解析器把 [::ffff:127.0.0.1] 规范化成了 ::ffff:7f00:1。如果你的分类函数只认点分十进制形式，这里就漏了。

技术 3：IP 字面量不该走 DNS

这是我在写 demo 时踩的坑。

第一版里，网关对所有 hostname 都调解析器。结果是：http://127.0.0.1/ 里的 127.0.0.1 被当成域名送去解析，解析器返回一个默认的公网地址，于是检查通过了。

修正：字面量直接返回自己，只有真正的域名才查 DNS。

function isIpLiteral(host) {
  return /^\d+\.\d+\.\d+\.\d+$/.test(host) || host.includes(':')
}

async function resolveHost(host, resolver) {
  const normalized = normalizeHost(host)
  if (isIpLiteral(normalized)) return [normalized]   // ← 不问 DNS
  return resolver.lookup(normalized)
}

为什么这个 bug 值得单独讲：它让"检查"变成了"检查解析器对字面量的处理"，而不是"检查用户要连的地址"。安全检查最危险的失败模式就是检查的对象和使用的对象不是同一个。

技术 4：DNS rebinding —— 时机问题

黑名单的第二种死法，也是这一章真正的主角。

天真的实现长这样：

① 解析 example.com → 得到 IP
② 检查这个 IP 是不是公网
③ 连接 example.com（这一步会**再解析一次**）

攻击者控制 example.com 的 DNS，让它这样回答：

  • 第 1 次解析 → 93.184.216.34（公网，检查通过）
  • 第 2 次解析 → 10.0.0.5（内网，真正的目标）

Demo 把两个实现并排跑：

▸ 天真实现：按域名连接
  ⚠️  放行 — 检查时 93.184.216.34，实际连到 10.0.0.5
     ❌ 这就是 DNS rebinding：检查的是一个 IP，连的是另一个

▸ 安全实现：连到检查过的那个 IP
  🛑 阻断 — 解析到 private (10.0.0.5)
     ✅ 因为它只解析一次：拿到的那个 IP 既用来检查，也用来连接

修法只有一句话：

const [ip] = await resolveHost(host, resolver)   // 只解析这一次
if (classifyIp(ip) !== 'public') return blocked
return tcpConnect(ip, host)                      // 连的就是刚才检查的那个 IP

连接目标用 IP，不用域名。HTTP 的 Host 头和 TLS 的 SNI 仍然带原域名，所以虚拟主机和证书校验都不受影响。

技术 5：L4 和 L7 都要看

官方列了检查的字段：

层 检查什么
L4 hostname、解析后 IP、最终 IP、port、protocol
L7 HTTP method、path、解码后的请求内容

两个细节：

  • "resolved and final IPs" —— 注意是"和"，不是"或"。解析出来的 IP 和实际连上去的 IP 都要看，这正是 DNS rebinding 防御在协议层面的表述。
  • "decoded request" —— 检查的是解码后的内容。如果只看原始字节，攻击者用 URL 编码、chunked、多重编码就能把 payload 藏过去。

Demo 跑出来

═══ 第一部分：SSRF 的几种写法 ═══
  🛑 直连本机                    (127.0.0.1)
  🛑 云元数据服务                (169.254.169.254)
  🛑 十进制写法                  (2130706433)
  🛑 十六进制写法                (0x7f000001)
  🛑 IPv4-mapped IPv6            (::ffff:7f00:1)
  🛑 内网 10.x                   (10.0.0.7)
  ⚠️  正常的公网地址              (api.github.com)

这一章要记住的

不是"有没有做检查"，而是"检查的和使用的是不是同一个东西"。

DNS rebinding 能绕过一大堆 SSRF 防护，就是因为它攻击的不是检查逻辑，而是检查和连接之间的时间差。同类问题在别处也有：检查文件路径再打开文件、检查 token 再用 token——任何"先检查后使用"的地方，都要问一句：中间它会不会变。

下一章讲 privsep：当攻击者已经能执行代码了，怎么让它执行的那段代码没有特权。

六、privsep：改参数没有用

代码：code/step6-privsep.mjs
官方来源：How We Built Safety Into Muse

我原以为"检查参数"就够了

工具收到一个请求，检查里面的 provider 字段是不是这个工具该用的——是就用，不是就拒绝。

这段代码的问题是：它在检查一个攻击者能控制的值，然后根据这个值去决定用哪份凭据。

Muse 的做法是让那个值根本不参与决定。

官方怎么说

The CLI running in the runtime cell only parses arguments, opens already allowed files on the caller's behalf, and passes typed arguments and file descriptors over a Unix socket to a worker. The actual privileged business logic runs in a systemd sandboxed worker outside the runtime cell.

Each worker is identified by its cgroup and has explicit credential allowlists. A calendar worker cannot ask authd for an email credential simply by changing a request parameter.

最后那句是整章的主旨。

技术 1：把"解析输入"和"使用特权"分开

privsep（特权分离） 是一个很老的设计思路（OpenSSH 是经典案例），核心是：

处理不可信输入的代码，不应该同时持有特权。

Muse 在 connector 上的落地：

角色 位置 权限 干什么
CLI runtime cell 内（不可信域） 调用者的权限 解析参数、打开已授权的文件、把 typed args + fd 递出去
worker runtime cell 外（host domain） 有凭据，但被收窄 执行真正的业务逻辑

CLI 里没有任何凭据。 它做不了 connector 的事——不是"被禁止做"，是它这一侧没有材料。

Demo 的验证：

▸ 攻击 B：CLI 想自己去找凭据
    CLI 自己持有的属性：[]
    ✅ CLI 里没有 authd 引用、没有凭据——它只能把请求转给 worker

技术 2：cgroup 身份 —— 内核给的，伪造不了

Worker 去 authd 取凭据时，authd 怎么知道它是谁？

用 cgroup。 每个 worker 在独立的 cgroup 里运行，authd 通过内核接口读取 caller 的 cgroup，据此判断身份。

为什么不用请求里的字段？因为字段是调用者写的。

请求里的 workerId cgroup
谁填写 调用者 内核
能不能改 能 不能
攻击者需要什么 改一个字符串 让内核相信它是另一个 cgroup

Demo 里的落地：

credentialFor(workerId, provider) {
  const allowed = WORKER_CREDENTIAL_ALLOWLIST[workerId]
  if (!allowed.includes(provider)) throw new Error(...)
  return this.#material.get(provider)
}

注意 provider 是 worker 从自己的身份推导出来的，不是从请求里读的：

const provider = this.#workerId.replace('-worker', '')
const credential = this.#authd.credentialFor(this.#workerId, provider)

这就是"改参数没有用"的机制：参数压根不在这条路径上。

▸ 攻击 A：日历 worker 改参数去要邮箱凭据
  ✅ 拦截：worker "calendar-worker" 的凭据白名单是 [calendar]，不含 "mail"
     注意拦截的依据是 worker 身份，不是参数内容。
     换句话说：改参数没有用，因为参数压根不参与这个决定。

技术 3：文件描述符传递 —— 权限判断留在有能力的那一侧

这里有个反直觉的地方。

Worker 有特权，但它的文件访问能力反而是被动的：它不自己打开文件，而是接收 CLI 递过来的 file descriptor。

CLI（调用者权限）                  worker（特权）
   │                                  │
   │ ① 想打开 /etc/shadow              │
   │    但它没有这个权限 → 打不开       │
   │                                  │
   │ ② 能打开的只有 /workspace/*       │
   │ ③ 把 fd 通过 Unix socket 递过去   │
   │ ────────────────────────────────▶│
   │                                  │ ④ 直接读写这个 fd
   │                                  │    不需要知道路径，也没有路径权限

Unix domain socket 上通过 SCM_RIGHTS 传 fd，接收方拿到的是文件本身，不是路径。 所以：

  • 调用者能打开什么，决定了 worker 能碰到什么
  • 权限判断发生在有能力判断的那一侧（CLI 知道调用者是谁）
  • worker 不需要一个"检查路径"的逻辑，它根本没有路径

Muse 用这个设计有一个很实际的理由：worker 是有特权的，所以不该给它一个"用户可控的路径字符串"。 它只接收已经打开的 fd。

Demo 验证：

▸ 攻击 C：CLI 想打开权限范围外的文件
  [CLI] 解析参数 method=read_file args={"path":"/etc/shadow"}
  ✅ CLI 无权打开 /etc/shadow（这是调用者权限范围之外的路径）

技术 4：三道独立判断

官方原文把这件事讲得很清楚：

Practically, this means there are three independent decisions being made: privsep decides where credential-capable code executes; authd decides which credential material an authenticated caller may obtain; and Sentinel decides whether an action may be taken.

判断 问题 组件
1 哪段代码能碰凭据？ privsep
2 这个调用者能拿到哪类凭据？ authd
3 这个动作能不能执行？ Sentinel

"independent" 是关键。如果这三件事由一个组件做，攻破它就是一次全破。分成三个之后，攻击者要同时在三个地方成功：

  • 绕过 privsep → 还要过 authd 的白名单
  • 骗过 authd → 还要过 Sentinel 的裁决
  • 骗过 Sentinel → 还是拿不到 authd 不给的凭据

这不是"三重检查"（那是同一个判断写了三遍），是三个不同的判断，各自管一件不同的事。

这一章要记住的

"改一个请求参数"是这类攻击的统一描述。

日历 worker 改参数去要邮箱凭据、低权限用户改 userId 去读别人的数据、普通工具改 role 去提权——都是同一个模式。

防御方式也统一：让那个参数不参与决定。

具体做法有两种：

做法 例子
用内核提供的身份 cgroup 标出 worker 是谁
用自己推导的值 provider 从 workerId 推导，不从请求读

两种都是"决定所依赖的输入，必须来自调用者控制之外"。

下一章讲一个更细的东西：即使进程是合法的、请求也通过了，它碰过什么也应该影响裁决。

七、tainted egress：让审批只在必要时打扰用户

代码：code/step7-tainted-egress.mjs
官方来源：How We Built Safety Into Muse

我原以为审批越严越好

每个网络请求都弹窗问用户——听起来最安全。

实际上不是。一个每次都要点确认的系统，和一个从不确认的系统，安全水平是一样的——因为用户会在第三天开始无脑点"允许"。

审批的价值取决于它出现的频率。太频繁 = 用户脱敏 = 等于没有。

所以真正的问题不是"怎么拦更多"，而是**"怎么在拦住危险请求的同时，让安全请求静默通过"**。

官方怎么说

Each tool execution process starts off as clean, until it reads user data, at which point it becomes tainted. Tainted processes lose their eligibility for narrowly-scoped auto-allow requests and enter the normal approval flow for network requests.

... implemented with eBPF cgroup programs for network interception and process attribution, and by attaching eBPF programs to Linux Security Module hooks to propagate taint.

一句话总结：不是看请求，是看请求是从哪个进程发出来的，以及那个进程碰过什么。

技术 1：eBPF 是什么

eBPF（extended Berkeley Packet Filter） 是 Linux 内核里的一个可编程执行环境。你在用户态写一小段程序，加载进内核，内核在特定事件上调用它。

三个关键性质：

性质 意味着什么
在内核里执行 用户态进程无法绕过，也无法篡改
有校验器 加载前静态检查，保证不会死循环、不越界访问
挂载点丰富 网络收发包、syscall、cgroup、LSM hook……

Muse 用到了两个挂载点。

挂载点一：cgroup 程序 —— 网络拦截与进程归因

cgroup（control group）是 Linux 用来给进程分组的机制。eBPF 可以挂在 cgroup 上，于是：

  • 该 cgroup 里所有进程的网络操作都会经过这段程序
  • 程序能把这次连接归因到具体是哪个进程发起的
  • 可以在这里放行、拒绝、或者记录下来

"process attribution"（进程归因）这个词是关键。 普通的防火墙只看五元组（源 IP、目的 IP、端口、协议），它不知道"是哪个进程"。有了 cgroup + eBPF，你能回答"这次连接是刚才读了用户邮件的那个进程发的"。

挂载点二：LSM hook —— 传播 taint

LSM（Linux Security Modules） 是内核里的一组安全检查点（SELinux、AppArmor 都挂在这上面）。eBPF 程序也可以挂上去，于是你能观察到：

  • 进程打开/读取了哪个文件
  • 进程 fork 出了谁

当观察到"读取了用户数据"时，就把这个进程标记为 tainted。

技术 2：taint 的语义是"降级"，不是"阻止"

这一点容易误解。看到"标记为污染"，直觉是"阻止它"。

实际语义是：

clean  进程 + 窄白名单 → 可以静默通过（auto-allow）
tainted 进程 + 同样的目的地 → 失去 auto-allow，走人工审批

taint 只是取消一个特权，不是加一个禁令。

这个设计的好处是渐进：不需要预先定义"什么数据算敏感"，只需要定义"什么样的请求可以免审批"。taint 负责把这个豁免收回去。

技术 3：白名单必须"窄"

const AUTO_ALLOW = [
  { host: 'api.github.com', path: '/repos/*/*/issues', methods: ['GET'] },
  { host: 'api.calendar.example', path: '/events', methods: ['GET'] },
]

三个维度都收窄了：host、path、method。

  • host 精确：不是 *.github.com
  • path 有模式：不是 /repos/*（那会包含删除仓库之类的写操作）
  • method 限定 GET：POST 一律不放行

为什么必须窄：auto-allow 是唯一一个"不经用户就出网"的通道。它宽一寸，taint 那一层就白做一大截。

我在写 demo 时就踩了这个：白名单写成 /repos/*/issues，正则只匹配一段路径，结果 GitHub 实际的 /repos/{owner}/{repo}/issues 是两段，白名单形同虚设——一个从来没生效过的豁免和一个很宽的豁免，问题是一样的。

对照实验

Demo 跑了四种情形：

── 情形 1：clean 进程请求白名单内的目的地 ──
  🟢 auto-allow — clean 进程 + 目的地在窄白名单内
     ↑ 用户没有被打扰——这就是这一层的价值

── 情形 2：同一个进程读了用户数据之后再出网 ──
  🟡 ask — 进程读过用户数据（tainted），失去 auto-allow 资格
     ↑ 目的地完全一样，但因为进程 tainted，降级为人工审批

情形 1 和情形 2 的请求完全相同——同一个 host、同一个 path、同一个 method。唯一的差别是发请求的进程之前干了什么。

这就是 taint 跟踪带来的新信息维度：

传统裁决依据 taint 之后的依据
输入 请求本身（五元组、path、body） 请求 + 发起者的历史
能回答 "这个请求危险吗" "发出这个请求的进程，刚刚碰过什么"

去掉 taint 跟踪会怎样——把 AUTO_ALLOW 当成唯一依据，情形 1 和情形 2 会得到完全相同的结论。也就是说：一个刚刚读完你邮箱的进程，可以静默地把数据发到 api.github.com。

⚠️ 本 demo 与真实实现的差异

做不了真的：这台机器是 macOS，没有 Linux 内核，装不了 eBPF。

我做的：把 eBPF 的观察点换成显式钩子调用，taint 的传播和裁决逻辑完全一致。

function observeRead(pid, path, isUserData) { ... }   // ← eBPF LSM hook 的等价物
function decideEgress(kernel, pid, target) { ... }    // ← eBPF cgroup 程序的等价物
真实（Linux） 本 demo（macOS）
谁观察"读了用户数据" eBPF + LSM hook，内核 显式函数调用
进程身份 内核给的 pid/cgroup 参数传入的 pid
能不能被绕过 不能 能（进程不调那个函数就没人知道）

差异只在"谁来观察"，不在"观察到之后怎么判断"。

而"谁来观察"恰恰是安全性所在——真实实现里进程无法选择不被观察，demo 里它可以。这是这一步唯一不能靠模拟跨过去的地方。

这一章要记住的

审批的目标不是"拦下所有危险操作"，而是"只打扰该被打扰的那部分"。

判断一个 agent 安全系统做得好不好，除了"能不能挡住攻击"，还要看第二个指标：

一个正常的、没有碰过用户数据的任务，用户需要点几次"允许"？

这个数字接近零，用户才会在真正需要时认真看那个弹窗。

下一章讲最后一件事：模型说"我做完了"的时候，系统怎么知道它是真的做完了。

八、状态机：模型只能解释状态

代码：code/step8-state-machine.mjs
官方来源：How We Built Safety Into Muse（activity audit trail 部分）

我原以为这是个小问题

模型说"已经帮你改好了"，但实际上补丁没打上。这算 bug 吗？重试一下就好了吧。

Muse 把它当架构问题处理。理由是：

agent 的自然语言天生倾向于"把已经开始说成已经完成"。 这不是模型在撒谎——它是在生成"最像答案的文本"。你说"帮我改个 bug"，它生成"已经改好了"作为回应，是因为那是最常见的回答形状。

所以问题不是"怎么让模型更诚实"（那是训练问题），而是**"完成"这件事由谁来说"**。

官方怎么说

Muse surfaces a full activity audit trail, letting users see completed and planned actions.

"completed" 和 "planned" 是两个不同的状态，而且是系统记录的，不是模型描述的。

技术 1：状态只能由执行系统产生

const LEGAL_TRANSITIONS = {
  queued:    ['running', 'canceled'],
  running:   ['waiting', 'completed', 'failed', 'canceled'],
  waiting:   ['running', 'canceled', 'failed'],   // ← waiting 不能直接到 completed
  completed: [],   // 终态
  failed:    [],   // 终态
  canceled:  [],   // 终态
}

三个设计点：

① waiting 不能直接到 completed。 等审批的时候，你不可能"完成"——因为动作还没执行。这条边不存在，就杜绝了"审批还在排队，回复却说已经做完了"。

② 终态是终态。 failed 和 completed 都没有出边。Demo 验证：

🛑 非法迁移：failed → completed（允许：无，终态）
   终态不能复活——否则"失败后被改写成成功"就成立了

③ 迁移只能通过一个方法。 transition(id, to) 检查合法性、记录审计轨迹、写证据，一步都不能跳。

技术 2：模型侧拿到的是只读 facade

和第四步的凭据 facade 是同一个模式：

function modelFacadeFor(runtime, taskId) {
  return Object.freeze({
    describe: () => runtime.snapshot(taskId),   // ← 只有读
    // 没有 setState / transition / markCompleted
  })
}

Demo 验证：

模型 facade 暴露的方法：describe
有没有 setState / transition / markCompleted？没有
✅ 模型这一侧根本没有能改状态的接口——这是能力隔离，不是检查

注意措辞：不是"模型不能改状态"，是"模型这一侧没有能改状态的对象"。

这是第三次出现同一个模式了：

步骤 隔离什么 怎么隔离
1 授权能力 控制面没有 grant 接口
4 凭据 cell 只拿到 facade
8 任务状态 模型只拿到 describe

一个系统里同一个模式出现三次，说明它是这个架构的基本原则，不是局部技巧。

技术 3：渲染时以事实为准

即使模型说错了，呈现给用户的内容也要以状态为准：

function renderResponse(modelText, snapshot) {
  const claimLooksDone = /(已完成|完成了|已修复|...)/.test(modelText)
  const actuallyDone = snapshot.state === 'completed'
  if (claimLooksDone && !actuallyDone) {
    return { corrected: true, text: `[已修正措辞] ${modelText}`, banner: `实际状态：${snapshot.state}` }
  }
  ...
}

跑出来：

▸ 模型把失败说成了成功
  模型说：parseDate 的时区问题已修复，测试都通过了
  🛑 实际状态：failed
     呈现给用户：[已修正措辞] parseDate 的时区问题已修复，测试都通过了

模型的话没有被替换掉，而是被标注了。 这个细节很重要：

  • 完全替换模型的话 → 丢失了它的解释价值
  • 原样显示 → 用户被误导
  • 标注 + 状态横幅 → 用户既看到模型的解释，也看到事实

技术 4：正交的失败分类

Muse 的失败不是"成功/失败"二元，而是一组正交的事实。官方在三态裁决里给了三个：

类别 含义
Lifecycle queued / running / waiting / completed / failed / canceled
Authority proposed / allowed / denied / ask / expired
Evidence tool_result / error / citation / artifact / approval receipt

"正交"的意思是它们可以任意组合：

  • 状态 failed + 授权 allowed + 证据 error → 授权没问题，是执行失败
  • 状态 waiting + 授权 ask → 卡在审批
  • 状态 completed + 授权 allowed + 证据 approval_receipt → 审批后成功

把它们压成一个枚举（比如只有 success / failure），信息就丢了：同样是失败，是"没被允许"还是"允许了但执行失败"，处理方式完全不同。

这和第三步讲 PTC 失败分类时是同一个道理：预算到期不是异常，中止不是超时，基底死亡两者都不是。

技术 5：action identity —— 审计轨迹的前提

createTask(label) {
  const id = `task_${++this.#nextId}`
  ...
}

每个动作有稳定 id，每次迁移都记：

task.transitions.push({ to, at: Date.now(), by })

Demo 输出：

任务 task_7 的证据：
  approval_receipt: approval_7 by user
每个动作都有稳定 id + 证据链，用户才能看到"完成了什么、计划做什么"

没有稳定 id，就没有审计轨迹。 你只能看到一堆"某处发生了某事"的日志，无法回答"用户问的那件事最后怎么了"。

这一章要记住的

模型是生成系统，它的输出"最像答案"而不是"最接近事实"。状态是执行系统的事实。

两者必须分开，而且渲染时以事实为准。

判断一个 agent 系统在这点上做得好不好，问一个问题：

模型能不能让"任务已完成"变成真的？

如果答案依赖"我们检查了它的措辞"，那答案是能。

# Muse 架构剖析：两个隔离域

作者： 饭团儿

日期： 2026年10月5日

## 一、问题

Meta 最近发布了 Muse，一个个人 AI 助理。

它跑在你的云电脑里，能读你的邮件，改你的日历，开浏览器，执行命令。

这东西怎么保证安全？

最容易想到的做法，是写一段严格的提示词，让模型别乱来。

再给每个工具加一道权限检查。

我以前就是这么干的。

干了半年，我发现这些做法有个共同点。

它们都跑在 agent 自己的进程里。

这就要命了。

假设模型被一段网页内容说服，让它去读 `~/.ssh/id_rsa`。

它会怎么干？

它会试着绕过那几道检查。

它可以直接改掉那个开关，也可以找一条你没检查的路径。

只要检查逻辑和被检查的东西待在同一个进程、同一份内存里，绕过就只是时间问题。

Muse 换了思路。

它不检查，它让 agent 根本拿不到。

## 二、两个域

Muse 跑在用户专属的一台云 VM 里。

这台 VM 被切成两个区。

一个区叫 runtime cell，里面跑 agent 本体，加上 workspace、文件、所有工具和二进制。

另一个区叫 host domain，里面是安全服务：查提示注入的分类器、凭据保管、连接器 worker，还有一个叫 Sentinel 的裁决器。

agent 在第一个区，裁决权在第二个区。

官方文档里有一句话概括这个设计：

> The right mental model is two isolated security domains on one box, not an LLM powered agent with root.

正确的理解是"一台机器上的两个隔离安全域"，不是"一个有 root 权限的 LLM"。

还有一句更关键：

> This split is important as the runtime cell is expected to process untrusted data.

这个切分很重要，因为 runtime cell 预期会处理不可信数据。

不是"万一被攻破怎么办"，是"假设它会被攻破"。

那么问题来了。

假设它被攻破，凭什么还能保证安全？

下面讲四个具体机制。

## 三、容器里的 root

Linux 有一种东西叫 user namespace。

它维护一张 uid 映射表。

你在里面看到自己是 0 号用户，也就是 root。

但内核做权限检查时，用的不是 0，而是映射表另一头的数字。

```
namespace 内    宿主上
   0      →      100000
   1      →      100001
```

所以你在容器里装包、改文件属主，看起来都是 root 在干。

但真正的权限检查落在宿主上一个普通用户身上，直接拒绝。

官方原话是：

> Root inside the runtime cell is mapped to an unprivileged host user so runtime cell root is not host root.

容器里的 root 映射到宿主上的非特权用户，所以它不是宿主 root。

这一条为什么重要？

因为容器逃逸的经典路径是：先在容器里拿到 root，再找个内核漏洞打成宿主 root。

有了 uid 映射，就算拿到容器内 root，宿主那边你还是 100000 号。

## 四、系统调用

第二个机制叫 seccomp。

一个进程可以往内核里装一小段程序。

此后它每次发起系统调用，内核都先跑这段程序，再决定放行还是拒绝。

返回 ALLOW 就放行，返回 ERRNO 就当这个调用不存在，返回 KILL 就直接杀进程。

这里有两个性质值得注意。

第一，只能收紧，不能放松。装上去就撤不掉，也不能再开新的白名单。

第二，它在内核里执行。被限制的进程没有任何办法绕开它，连发起那个调用的资格都没有。

Muse 用它关掉了一个东西：`io_uring`。

> It also gets ... filtered system calls (for example no `io_uring`).

`io_uring` 是 Linux 的高性能异步 IO 接口。

它和普通系统调用不一样。提交任务不用每次陷入内核，而是写进一块共享内存的环形缓冲区，内核在后台自己取。

这带来两个问题。

一是很多操作不走常规系统调用路径，按系统调用检查的传统手段看不到它。

二是它自己历史上出过好几次严重漏洞，是容器逃逸的常见入口。

所以 Muse 直接把它关掉。

这个思路值得记下来。

安全上遇到复杂的东西，第一反应不该是"怎么过滤它"，而是"我需不需要它"。

不需要就整个关掉，比逐条过滤可靠得多。

## 五、权限开关

传统 Unix 里 root 是一整块。

要么什么都能干，要么什么都干不了。

Linux 把它拆成了大约四十个独立的开关，叫 capabilities。

每个开关管一类特权。

`CAP_SYS_PTRACE` 允许你 ptrace 别的进程，也就是读别人的内存。

`CAP_NET_ADMIN` 允许你改网络接口、路由表和防火墙规则。

`CAP_SYS_ADMIN` 能 mount，能改 cgroup，实际上就是新的 root。

Muse 的容器丢掉了前两个。

> ... and limited kernel capabilities (for example no `CAP_SYS_PTRACE` and no `CAP_NET_ADMIN`).

`CAP_SYS_PTRACE` 必须丢，因为它直接威胁"两个域"这个设计。能读别的进程内存，就能读控制面的秘密。

`CAP_NET_ADMIN` 也必须丢，因为它威胁出口策略。能改路由表，就能绕过代理把数据发出去。

注意这两件事可以同时成立。

你在容器里是 uid 0，同时你没有这两个开关。

权限被拆开之后，"是 root"这句话就不再有单一含义了。

## 六、通道

agent 总要和外面的服务说话。

这里的问题是：服务端怎么确认对面是谁。

常见的做法是发一个 token。

但 token 本身是个秘密，放在通道上就可能被偷。

Muse 用的是 Unix domain socket，加上一个叫 `SO_PEERCRED` 的机制。

它的工作方式是这样。

服务端调用它，内核直接告诉服务端，连接过来的那个进程是谁，pid、uid、gid 全都有。

关键在于这个信息由内核填写，对端无法伪造。

进程不能声称自己是别的 uid。

于是服务端可以据此做权限判断，而且通道上不需要放任何秘密。

官方文档说：

> All communication between the runtime cell and other services in the VM happens via Unix domain sockets with `SO_PEERCRED` and peer ACLs. This provides kernel authenticated, least-privilege interprocess communication with no secrets to steal.

最后四个词是重点：没有可偷的秘密。

如果一个通道本身不含秘密，那它就没有可偷的东西。

这和"我们不把秘密告诉别人"是两码事。

## 七、动手验证

我把这套东西在本机实现了一遍，代码在 `code/step1-trust-domains.mjs`。

它起两个进程。

一个扮演 host domain，持有凭据，只暴露一个接口。

另一个扮演 runtime cell，跑在操作系统沙箱里，通过 Unix socket 和前者说话。

三个攻击场景。

```
【Host domain 已就绪】持有凭据，只暴露 propose
  控制面 socket 权限：0600（只有同 uid 的进程能连）
  ── 攻击面 1：直接从文件系统偷凭据 ──
     被挡住：EPERM（内核拒绝，不是我们的代码在检查）
  ── 攻击面 2：让控制面给自己发许可证 ──
     unknown op: grant — 控制面不提供授权接口——授权只能来自用户
```

第一条是真的内核级拒绝。

macOS 上对应 Linux 那套东西的叫 Seatbelt。策略由内核执行，cell 进程没有任何办法绕开。

它不是"我们的代码检查后拒绝"，是内核让 `readFileSync` 直接返回 EPERM。

第二条更有意思。

控制面根本不存在 grant 这个操作。

不是"它检查后拒绝了"，是"没有那条代码路径"。

这两件事差别很大。

拦截式的做法，写一段检查逻辑，发现越权就返回错误。它被绕过的前提是检查有漏洞。

无路径式的做法，干脆不实现那个能力。它被绕过的前提是找到一段不存在的代码。

代码越长，第一种做法越危险。

你新增一条调用路径，就有可能忘了在那里加检查。

第二种不存在这个问题。

## 八、一个质疑

有人看到这里会想：搞这么复杂，值得吗。

这个质疑有道理。

systemd-nspawn、user namespace、seccomp、capabilities，配起来确实麻烦。

而且这些机制都有过绕过漏洞。

我的看法是：它们防的不是"一定会被攻破"，而是"攻破之后能走多远"。

官方自己也是这么说的。

> Muse can and will still make mistakes, but we expect they'll be much less frequent and cause much less damage due to the safety systems we've built in.

Muse 会犯错，这是肯定的。

但因为这些安全系统的存在，我们预计错误会少得多，造成的损失也会小得多。

目标不是不出错。

目标是出错也没关系。

反过来看那些只靠提示词的系统，它们赌的是模型永远不被说服。

这个赌注在模型能力越来越强的今天，只会越来越贵。

## 九、一个坑

最后讲个我自己踩的。

第一版 demo 没挡住。

cell 明明在沙箱里，却读到了宿主凭据。

查了半天才明白。

macOS 上 `/var` 是 `/private/var` 的符号链接。

我生成的临时目录路径是 `/var/folders/...`，写进拒绝规则用的也是这个。

但 Seatbelt 按解析之后的真实路径匹配，实际是 `/private/var/folders/...`。

两条路径对不上，规则静默失效。

改法是一行：

```js
const workDir = realpathSync(mkdtempSync(join(tmpdir(), 'muse-')))
```

这件事值得单独说，因为它代表了安全代码最危险的失败模式。

策略写对了语法，但没写对路径。

程序不报错，测试不报错，攻击直接成功。

后面每一步我都会遇到同类问题。

检查的和使用的不是同一个东西。

## 十、总结

Muse 这个设计里，最值得学的不是某个具体机制。

是一个习惯。

写完一段安全检查，问自己一句：这段检查如果失效了，会有人知道吗。

如果答案是"没有"，那就想想，能不能换成一个"失效了也拿不到东西"的设计。
